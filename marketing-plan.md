# Neurofoundry Marketing Plan

## Repo Readout

Neurofoundry already presents three strong commercial hooks:

- `home.html` frames the brand as "systems that think, adapt, and deliver."
- `forge_final.html` gives the product a concrete interactive surface.
- `crew.html` positions custom AI deployment as a paid service.

The current gap is not lack of ambition. It is funnel clarity. The site reads like a lab plus portfolio, while the project direction points toward a Comet-like browser product with prompt-driven automation and browser extension usage as the preferred user path.

This plan treats Neurofoundry as:

- A browser-native automation product for power users and operator teams.
- A premium custom deployment studio for buyers who need the product adapted to their workflow.
- A high-trust technical brand that sells both software and execution capability.

## Positioning

### Core Thesis

Neurofoundry turns a user prompt into a browser workflow that can be reviewed, executed, and deployed through a browser extension or a managed pilot.

### Primary Promise

Move from "describe the task" to "the browser did the work" without forcing buyers to stitch together scripts, agents, prompts, and brittle automations themselves.

### Messaging Pillars

1. Prompt to execution
   Users describe an outcome, not a script.
2. Browser-native control
   The product lives where work already happens: tabs, forms, dashboards, and web apps.
3. Human-in-the-loop reliability
   Runs can be reviewed, approved, and corrected instead of blindly fired.
4. Custom deployment path
   Teams can start with the extension and graduate into workflow-specific deployments.
5. Engineered, not generic
   The brand should keep emphasizing precision, systems design, and production readiness.

## Ideal Customer Profiles

### ICP 1: Founder Operators

- Pain: Too many repetitive browser workflows across sales, hiring, support, and research.
- Trigger: They already use AI, but their browser work still depends on manual tab juggling.
- Offer: Fast pilot plus direct founder access.

### ICP 2: Revenue and Growth Teams

- Pain: Lead research, CRM updates, enrichment, and outbound prep are repetitive and slow.
- Trigger: Need more pipeline without growing headcount at the same rate.
- Offer: Extension-led pilot focused on prospecting and account research.

### ICP 3: Recruiting and Talent Teams

- Pain: Sourcing, profile review, outreach prep, and candidate tracking live in browser tabs.
- Trigger: They need speed but cannot tolerate hallucinated actions.
- Offer: Reviewable automations with approval steps and audit trails.

### ICP 4: Research, Operations, and Analyst Teams

- Pain: Gathering, comparing, and summarizing web information across multiple sources is slow.
- Trigger: Repeated workflows with high tab volume and context loss.
- Offer: Browser workflows that extract, compare, and route output into structured handoff.

## Offer Ladder

### Tier 1: Request Access

- Goal: Capture high-intent visitors and waitlist interest.
- CTA: `signup.html`
- Promise: Early access to the browser workflow product.

### Tier 2: Guided Pilot

- Goal: Sell a paid or qualified pilot around one workflow.
- CTA: `crew.html` or a direct "Book a pilot" follow-up flow.
- Promise: One automation flow, deployed around the buyer's stack.

### Tier 3: Custom Deployment

- Goal: Convert operational teams with more complex workflow needs.
- CTA: `crew.html` plus case-study proof.
- Promise: Persistent memory, custom logic, workflow-specific deployment.

### Tier 4: Enterprise Expansion

- Goal: Turn pilots into multi-team rollouts.
- CTA: direct outreach and account-specific demos.
- Promise: Governance, security, human approval gates, and deployment support.

## Funnel Architecture

### Top of Funnel

- `home.html` should sell the category: prompt-driven browser execution.
- `projects.html` should prove system capability and map to business use cases.
- `technology.html` should build technical trust for skeptical buyers.

### Middle of Funnel

- `sales-prototype.html` should act as the interactive proof asset.
- `crew.html` should position custom deployment as the premium path.
- `neurofoundry-report.html` and `gallery.html` should be supporting proof, not primary conversion assets.

### Bottom of Funnel

- `signup.html` should capture access requests.
- Follow-up should route buyers into one of two tracks:
  - Extension access
  - Guided pilot / deployment conversation

## Website-Level Recommendations

### Message Corrections

- Lead with browser workflows, not generic AI language.
- Use "browser extension" and "prompt to action graph" language consistently.
- Make one workflow tangible on the first screen: sales prospecting, hiring research, support triage, or operations research.

### Conversion Corrections

- Add one dominant CTA across key pages: request access or start pilot.
- Make proof pages point back into the core CTA instead of dead anchors or generic portfolio language.
- Keep Home / Forge / Projects as the stable nav spine on any newly touched surface.

### Proof Corrections

- Turn existing technical capability into business proof:
  - Prompt -> plan -> browser action -> structured output
  - Human review gates
  - Custom deployment when extension-only is not enough

## Campaign Plan

### Phase 1: Clarify the Product Story

Duration: 2 weeks

- Publish the interactive prototype as the sales narrative anchor.
- Update outreach and on-site copy to emphasize browser extension usage.
- Use one hero statement everywhere:
  - "Turn a prompt into a browser workflow your team can review and run."

### Phase 2: Prove One Workflow Per Persona

Duration: 3 weeks

- Sales workflow:
  - find accounts
  - enrich
  - draft outreach
  - push to CRM
- Recruiting workflow:
  - source profiles
  - score fit
  - draft outreach
  - route to ATS
- Research workflow:
  - open sources
  - compare findings
  - summarize
  - hand off report

Each workflow needs:

- one short landing-page proof block
- one 30-60 second demo clip or mockup
- one outbound email angle
- one social post or carousel

### Phase 3: Pilot Conversion

Duration: 4 weeks

- Run direct outreach to founder operators and team leads.
- Offer a narrow pilot tied to one browser workflow.
- Use a fixed promise:
  - reduce repeated browser work
  - keep human approval in the loop
  - deploy against the buyer's actual stack

## Browser Extension Validation

Because the preferred usage model is browser extension based, testing and demos should reflect that path instead of generic website browsing.

Validation checklist:

- Demo the extension workflow from a user prompt, not from manual admin controls.
- Show at least one review checkpoint before final action.
- Confirm the output is routed into a recognizable business destination.
- Test the sales prototype in desktop browser widths and mobile widths.
- Use the prototype as the sales narrative, then map buyers into extension or pilot next steps.
